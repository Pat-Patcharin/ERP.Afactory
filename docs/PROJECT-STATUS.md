**PR2a คืออะไร** — โปรโมชั่นเลิกเป็นค่าคงที่ในไฟล์ราคา กลายเป็น entity ที่มี
ทะเบียน หน้ารายการ หน้ารายละเอียด และด่านสิทธิ์ 4 ข้อบนฟังก์ชันที่เขียนข้อมูล
ไม่ใช่บนปุ่ม

1. `mayCreatePromotion` — บทบาทที่สร้างได้อ่านจากตารางสิทธิ์ ไม่ใช่รายชื่อในโค้ด
2. `mayApprovePromotion` — คนสร้างอนุมัติของตัวเองไม่ได้ · หลุดราคาขั้นต่ำ
   หรืองบเกินเพดานต้องขึ้นผู้จัดการ
3. `mayEditPromotion` — โปรที่ใช้งานอยู่แก้ไม่ได้ ต้องหยุดชั่วคราวก่อน
4. `applyPromotionPatch` — ทางเขียนทางเดียว ตั้งธง `dirtySinceApproval`
   เมื่อแตะฟิลด์ใน `PROMOTION_CONDITION_FIELDS` แก้เงื่อนไขระหว่างหยุด
   = ต้องอนุมัติใหม่

**PR3b คืออะไร** — โปรแถมสินค้าตั้งค่าได้ครบตั้งแต่รอบแรก แต่ไม่มีที่กรอก
"ซื้อเท่าไหร่ แถมเท่าไหร่" เลย ขั้นเข้าระบบได้ทางเดียวคือเขียนลงไฟล์ข้อมูล

- **รูปแบบย่อยบังคับเลือก ไม่มีค่าเริ่มต้น** รายตัว · ชุดที่กำหนด — แบบกลุ่ม
  ไม่อยู่ในรายการ **และถูกปฏิเสธที่ `applyPromotionPatch`** เพราะรายการที่ซ่อน
  ยังส่งมาทาง `?scope=group` ได้ พร้อมโน้ตบอกว่ามีแบบที่สามและปิดเพราะยังไม่
  ตัดสินว่า "ถูกที่สุด" วัดจากราคาไหน
- **ฝั่งของแถมแยกจากฝั่งเงื่อนไข** `freeItems` / `freeGroup` เป็นฟิลด์ใหม่และ
  อยู่ใน `PROMOTION_CONDITION_FIELDS` — เปลี่ยนของแถมคือเปลี่ยนเงื่อนไข ธง
  `dirtySinceApproval` จึงต้องติด แบบรายตัวไม่ถามซ้ำเพราะของแถมคือตัวเดียวกัน
- **ตารางขั้น** คอลัมน์ `ซื้อ (จ่ายจริง)` · แถม · รวมที่ได้รับ · ราคาเฉลี่ย
  ราคาเฉลี่ยเป็นคอลัมน์คำนวณและ **ขึ้นสี `text-danger` ทันทีที่ต่ำกว่า
  `price_last`** ตอนพิมพ์ ไม่ต้องบันทึก — `GridCol.get` รับแค่ row จึงไม่เห็น
  ราคาสินค้าที่อยู่ในอีกกริด ทางออกคือสร้าง `cols` ข้างใน `blocks(s)` ให้
  closure ปิดทับ state ไม่ต้องแตะ engine
- **`tiers` เข้า `toPatch()` แล้ว** ซึ่งเปิดช่องใหม่: ก่อนหน้านี้มันไม่อยู่ใน
  patch จึงไม่มีทางถูกล้าง มีเทสต์ปักไว้ว่าแก้โปรที่มีขั้นอยู่แล้วโดยไม่แตะ
  ตารางขั้น ขั้นเดิมต้องอยู่ครบ — รูปแบบเดียวกับที่เจอตอน A2a
- **ช่องบังคับวัดต่อชนิด** `required` ดิบเป็น 10 รายการ แต่ขั้นของแถมกับขั้น
  ส่วนลดไม่เคยบังคับพร้อมกัน คนกรอกโปรหนึ่งใบเห็นไม่เกิน 9 เทสต์เดิมที่นับ
  ความยาว array ถูกยกระดับให้นับต่อชนิด ซึ่งเป็นตัวเลขที่ตรงกับเกณฑ์จริง

**ก้อนที่ 1 ของรอบชนิดที่สอง คืออะไร** — โปรส่วนลดราคาใช้งานได้ตั้งแต่หน้า
เลือกประเภทถึงหน้ารายละเอียด โดยยังไม่แตะบรรทัดสินค้าในเอกสาร

- **ตัวคำนวณอยู่คนละไฟล์กับของแถม และห้ามเรียกข้ามกัน** — `tierFor` ตอบว่า
  จำนวนตกอยู่ในขั้นไหน (ขั้นไม่ผสม) `bestLadder` จับคู่ขั้น (ขั้นผสมได้)
  เทสต์อ่านบรรทัด import ของทั้งสองไฟล์เพื่อกันการรวมทีหลัง
- **กฎ min()** `effectiveUnitPrice(ราคาที่ชนะ, ราคาโปร)` — โปรแข่งกับราคาตั้ง
  และแพ้ได้ สี่เคสของสเปค §1.4 เป็นเทสต์สี่ข้อ เท่ากันพอดีไม่นับว่าโปรมีผล
- **เปอร์เซ็นต์คิดจากราคามาตรฐานเท่านั้น** ฉีดของผิดให้คิดจากราคาชั้นนั้นเอง
  แล้วดีลเลอร์ได้ 391 แทน 460 = ส่วนลดซ้อนที่ไม่มีใครสั่ง เทสต์แดง
- **เตือนสองอย่างจาก state ตอนพิมพ์** ราคาหลังลดหลุด `price_last` · และชั้น
  ลูกค้าที่โปรนี้ไม่มีผลเลย คำนวณจากราคากลางจริง (`PM-0007` ในข้อมูลตัวอย่าง
  คือโปรที่ขั้นถูกสุด 470 ยังแพงกว่าราคาดีลเลอร์ 460)
- **`promotionFloorBreaches` ตัดที่ชนิดแล้ว** ก่อนหน้านี้วน `p.tiers` โดย
  สมมติว่าเป็นของแถมเสมอ และจะคิดราคาเฉลี่ยของขั้นที่ไม่มีอยู่จริงไปตัดสินว่า
  ใครอนุมัติได้ — โปรส่วนลดที่หลุดขั้นต่ำใช้ `promotionDiscountBreaches` แทน
  และยังขึ้นผู้จัดการเหมือนกัน
- **`freeGoodsWarehouse` บังคับเฉพาะชนิดที่ให้ของ** ส่วนลดราคาไม่หักสต๊อก
- กล่อง `note` ของ form engine ไม่มีระดับความรุนแรง (สีเดียวเสมอ) รอบนี้ห้าม
  แตะ engine จึงบอกระดับด้วยข้อความ

**PR2b คืออะไร** — ฟอร์มสร้าง/แก้โปรตาม §6b ห้ากลุ่ม กลุ่มงบกับคลังแยกเป็น
แท็บของตัวเองเพราะเป็นเรื่องเงิน ไม่ใช่เงื่อนไขการใช้ ฟอร์มไม่มีกฎอยู่ในตัวเอง
ทุกการเขียนไปที่ `createPromotion` (สร้าง) และ `applyPromotionPatch` (แก้)

- **`createPromotion`** ขั้นที่ขาดไปของ PR2a — `mayCreatePromotion` เพิ่งได้
  ผู้เรียกจริงตัวแรก คืน `reason` เมื่อถูกปฏิเสธเพื่อให้หน้าจอบอกได้ว่าทำไม
  และถอนแถวออกถ้าเขียนไม่ผ่าน ไม่ปล่อยโปรเปล่าค้างในทะเบียน
- **`nextPromotionCode`** ลอกตรรกะจาก `nextPRCode` (`split("-")[1]`) ไม่ใช่
  `nextBPCode` (`replace(/\D/g,"")`) — วันนี้ให้ผลเท่ากัน แต่ถ้าเติมปีเป็น
  `PM2506-0001` แบบ BP จะอ่านได้ 25060001
- **ช่องบังคับ 8 ช่อง** และสี่ช่องห้ามมีค่าเริ่มต้น: เหตุผลที่สร้าง (ตัวเลือก
  ตายตัว) · คลังที่หักของแถม · ฐานคิดค่าคอม (อยู่ในกล่องที่บอกว่ากระทบรายได้
  พนักงาน) · งบคิดจากต้นทุนหรือราคาขาย
- **สองบั๊กที่เทสต์จับได้** `findDuplicates` เคยใช้ `require()` ในโมดูลฝั่ง
  ไคลเอนต์ ทำให้พิมพ์ชื่อโปรถึงตัวที่สี่แล้วฟอร์มพัง · ประเภทที่เลือกจาก
  หน้าก่อน (`?kind=`) ไม่ได้ถูกส่งต่อ ทุกโปรจะกลายเป็น "แถมสินค้า" เงียบ ๆ

## สิ่งที่ยังไม่ได้ทำ และอยู่นอกงานทุกรอบที่ผ่านมา

งานห้ารอบที่ผ่านมาทั้งหมดอยู่บน**ข้อมูลในหน่วยความจำ** ไม่มีฐานข้อมูล ไม่มี API
ไม่มีการล็อกอินจริง สิ่งเหล่านี้ไม่ใช่ backlog เพราะไม่ใช่งานที่เลื่อนไว้
แต่เป็นชั้นที่ยังไม่เคยเริ่ม

### ฐานข้อมูล

ทุกอย่างเป็น array ใน `data/*.ts` แก้แล้วหายเมื่อ reload
สิ่งที่ต้องตัดสินก่อนเริ่ม

- **Primary key** `product_code` ว่างได้ 51 แถว และมี 5 รหัสซ้ำ (`H-RC005-01`
  ร้ายแรงที่สุด — ผูกกับสินค้าคนละตัว) ต้องเคลียร์ก่อนใส่ unique constraint
- **เลขที่เอกสาร** ตอนนี้ `nextSeq()` นับจาก array ในหน่วยความจำ
  ของจริงต้องเป็น sequence ที่กันชนกันตอนมีผู้ใช้พร้อมกัน
- **สอง code space** ของข้อมูลตัวอย่าง (backlog N-4) ต้องรวมก่อน migrate
  ไม่งั้นจะขน foreign key ที่ชี้ไปที่ไม่มีอยู่จริงเข้าฐานข้อมูล
- **Audit trail** ตระกูลเอกสารขาออกยังไม่มี (backlog ข้อ 4) — ถ้าจะมี
  ควรออกแบบพร้อมกับ schema ไม่ใช่เติมทีหลัง

### นำเข้าข้อมูล

`CLAUDE.md` วางกรอบไว้แล้วเป็น pipeline 6 ขั้น
Source → Map → Normalize → Validate → Preview → Commit แต่ยังไม่ได้เขียน

- ขั้น Validate ใช้ `validateItem()` จาก `pricing.ts` ที่มีอยู่แล้ว
- ตาม pattern เดิม: **import ทุกแถวแล้ว flag error ไม่ drop แถวทิ้ง**
- อ่าน CSV ด้วย SheetJS ต้องใช้ `{ header: 1, raw: false }` ไม่งั้นเลข 0 นำหน้าหาย
- **นี่คือที่ที่ backlog ข้อ 11 ต้องถูกแก้** — รหัสสินค้าหนึ่งชุดข้าม
  product master · price master · เอกสาร ไม่ใช่แก้ที่ mock

## กฎที่งานทุกรอบนี้สอน

อยู่เต็มใน [`BACKLOG.md`](./BACKLOG.md) หัวข้อบนสุด สรุปสั้น ๆ

1. **กฎที่เขียนครบแต่ไม่กัดใคร** เจอซ้ำตลอดสามรอบ — รายการที่ยืนยันแล้วอยู่ใน
   `BACKLOG.md` หัวข้อบนสุด 7 ตัว บวกกับที่กระจายอยู่ในแต่ละข้อ (`noCost` ·
   กฎคู่ค้า Draft · `pickComplete`/`packComplete` ที่ไม่มี guard · ตระกูล `isOverX`)
   เวลาเพิ่มกฎ ต้องมีเทสต์ที่พิสูจน์ว่ามีเคสถูกปฏิเสธจริง **และ**
   ต้องมีข้อมูลที่เดินไปถึงกฎนั้นได้
2. **คอมเมนต์ที่โค้ดไม่ทำตาม** อันตรายกว่าไม่มีคอมเมนต์
3. **งาน refactor: ย้ายของเดิมก่อน ห้ามเขียนใหม่ให้เหมือน** แล้วไล่เทียบทีละบรรทัด
   — "เทสต์เขียว" กับ "ไม่เปลี่ยนพฤติกรรม" ไม่ใช่เรื่องเดียวกัน
4. **เทสต์แนวห้าม ต้องฉีดของผิดเข้าไปดูว่าแดงจริงก่อนเชื่อ**
5. **ข้อ backlog ที่พิสูจน์ด้วยโค้ดได้ ให้เขียนเทสต์ที่แดงเมื่อมันถูกแก้**
   เพื่อให้ backlog เตือนตัวเองตอนหมดความจำเป็น
6. **อย่าเขียนตัวเลขจากความจำ** ใช้กับ contrast ratio เท่ากับที่ใช้กับโค้ด
7. **เจอของที่ทำเรื่องนั้นอยู่แล้ว ให้หยุดถามก่อนสร้างใหม่** — กฎนี้กันงานซ้ำ
   ไปได้ทั้งรอบหนึ่งครั้ง
8. **"ร้ายที่สุด" เป็นสมมติฐาน ไม่ใช่ข้อเท็จจริง — วัดก่อนเชื่อ แม้จะเป็นคำของเราเอง**
   A1 บันทึกว่า `revisions` ที่เป็น undefined ร้ายที่สุดในเจ็ดฟิลด์ที่หายไป
   วัดจริงที่ A1c แล้วไม่ร้าย ผู้อ่านทั้งสามที่กัน `??` ไว้หมด และ `??=`
   ที่จุดเขียนซ่อมฟิลด์ให้เองตั้งแต่การใช้งานครั้งแรก
   เป็นรูปแบบเดียวกับ contrast ratio ที่จำมาผิดในข้อ 6 — ตัวเลขที่จำมาผิดได้
   ความร้ายแรงที่เดาเอาก็ผิดได้เท่ากัน และมันพาให้เรียงลำดับงานผิดทั้งรอบ
