## 0. สรุปสั้น ๆ ว่าต้องทำอะไร

Flow ที่ต้องการ **ต่างจากที่โค้ดทำอยู่ตอนนี้** ใน 3 เรื่องหลัก

| เรื่อง | โค้ดตอนนี้ | ที่ต้องการ |
|---|---|---|
| ปลายทางของ Quotation | แปลงเป็น **S/R เท่านั้น** (`qtConvert` → "Convert to Sales Request") | แปลงเป็น **S/O ได้โดยตรง** เมื่อลูกค้าตอบรับ |
| การอนุมัติ Quotation | **ไม่มี** — มีแค่ Send / Accept / Reject / Convert | ต้องผ่าน admin อนุมัติ ก่อนส่งลูกค้า |
| ลายเซ็น + ตราประทับบน PDF | **ไม่มีเลยในระบบ** | ออก PDF ที่มีลายเซ็นและตราประทับหลัง approve |

ส่วนที่ **มีอยู่แล้ว ไม่ต้องสร้างใหม่**

- S/R มี state machine ครบ: `srSubmit` `srApprove` `srReject` `srConvert` `srReopen` `srCancel`
- S/R มีร่องรอยการอนุมัติแล้ว: `approvedBy` `approvedDate` `rejectReason` `soRef` `history[]`
- S/R แสดง available stock และจำนวนที่ขาดอยู่แล้ว ผ่าน `availabilityFor(code, qty)` → `{ available, shortBy }`
- S/O มี `soConfirm` `soApproveCredit` `soCreatePick` และสถานะ `Partially Delivered` สำหรับ back order
- ระบบสิทธิ์มีอยู่แล้วที่ `lib/permissions.ts` + `lib/domain/admin.ts` (11 roles, 6 data scopes)

## 1. เรื่องที่ต้องตัดสินใจก่อนเริ่มเขียนโค้ด

**อย่าเพิ่งให้ Claude Code เริ่มเขียนจนกว่าจะตอบ 5 ข้อนี้ได้** เพราะแต่ละข้อเปลี่ยนโครงสร้างข้อมูล

### D1 — Quotation ไปไหนต่อ

เลือกหนึ่ง:

- **(ก) QT → S/O ตรง** ตามที่อธิบาย — S/R ใช้เฉพาะเคสที่ลูกค้าไม่เอาใบเสนอราคา
- **(ข) QT → S/R → S/O เสมอ** ตามที่โค้ดทำอยู่ — S/R เป็นด่านอนุมัติเดียวของระบบ

ถ้าเลือก (ก) ต้องยอมรับว่า **มีด่านอนุมัติ 2 ทาง** ที่ต้องดูแลให้กฎเหมือนกัน
ถ้าเลือก (ข) ก็คือย้ายการอนุมัติไปไว้ที่ S/R ที่เดียว แก้โค้ดน้อยกว่ามาก

> ข้อเสนอ: เลือก (ก) ตามที่ออกแบบไว้ แต่ให้ **QT ที่ approve แล้ว = ราคาถูกอนุมัติแล้ว**
> ดังนั้นตอนแปลงเป็น S/O ไม่ต้องอนุมัติราคาซ้ำ เหลือแค่เช็คเครดิตกับสต๊อก

### D2 — ใบที่ approve แล้ว แก้ได้อีกไหม

ถ้าแก้ราคาได้หลัง approve **ลายเซ็นกับตราประทับจะไม่มีความหมาย** เพราะเอกสารที่ลูกค้าถือกับในระบบจะไม่ตรงกัน

> ข้อเสนอ: approve แล้ว **ล็อกทุกบรรทัด** แก้ไม่ได้
> ถ้าจะแก้ต้องกด "ขอแก้ไข" → สถานะกลับเป็น Draft → เลข revision +1 → ต้อง approve ใหม่
> PDF เดิมยังเก็บไว้ในประวัติ ไม่ลบทิ้ง

### D3 — Admin คนเดียวอนุมัติได้ทุกอย่างจริงหรือ

ในรูปเขียนไว้ว่า ราคาต่ำกว่า Pricelist ขั้นต่ำ → ต้องให้ **Manager** อนุมัติ
แต่ระบบตอนนี้แบ่งแค่ 2 บัญชี คือ sale rep กับ admin — **ยังไม่มีบทบาท Manager ที่แยกออกมา**

ต้องเลือก:
- เพิ่มบทบาทที่ 3 (Sales Manager) เข้าไปจริง ๆ หรือ
- ให้ admin ทำหน้าที่ทั้งสองระดับไปก่อน แล้วค่อยแยกทีหลัง

### D4 — ลูกค้าใหม่ที่เซลล์กรอกเอง เก็บที่ไหน

ในรูปเขียนว่า "ข้อมูลยังไม่เข้า BP master ต้องให้ admin ยืนยันก่อน"
ระบบตอนนี้ **ไม่มีสถานะรอยืนยัน** — `BP_TONE` มี Active / Inactive / On Hold / Blocked / Draft

> ข้อเสนอ: ใช้สถานะ `Draft` ที่มีอยู่แล้วเป็น "รอ admin ยืนยัน"
> และเพิ่มกฎ: คู่ค้าสถานะ Draft **เปิด S/O ไม่ได้** (เปิด QT หรือ S/R ได้)
> เหตุผล: QT ยังไม่ผูกพัน แต่ S/O จองของจริงและผูกกับเครดิต ต้องมีตัวตนที่ยืนยันแล้ว

### D5 — available stock ที่เห็นใน S/R เชื่อได้แค่ไหน

S/R **ไม่จองของ** แต่ S/O **จองของ** ตามที่ออกแบบไว้ถูกแล้ว
แต่จะเกิดกรณีนี้: S/R สองใบเห็นของเหลือ 10 ชิ้นเท่ากัน อนุมัติทั้งคู่ ใบที่สองเปิด S/O แล้วของไม่พอ

> ข้อเสนอ: ตอนกด generate S/O ให้ **เช็คสต๊อกซ้ำอีกรอบเสมอ**
> ถ้าของไม่พอแล้ว ให้เตือนและถามว่าจะเปิดเป็น back order หรือยกเลิก
> ห้ามใช้ตัวเลขที่ค้างอยู่ในหน้าจอ S/R ตอนอนุมัติ

## 2. State machine ที่ต้องการ

### 2.1 Quotation

```
Draft ──submit──> Pending Approval ──approve──> Approved ──send──> Sent
  ^                      │                         │                 │
  │                      └──reject──> Rejected     │          ┌──────┴──────┐
  └────────request revision───────────────────────-┘     Accepted      Rejected
                                                              │      by customer
                                                       convert│
                                                              v
                                                        Sales Order
```

สถานะที่ต้องเพิ่มเข้า `QT_TONE` ใน `lib/badges.ts`

| สถานะใหม่ | tone | ความหมาย |
|---|---|---|
| `Pending Approval` | `warning` | เซลล์ส่งขออนุมัติแล้ว รอ admin |
| `Approved` | `success` | admin อนุมัติแล้ว มี PDF ที่ลงนามแล้ว ส่งลูกค้าได้ |
| `Revision Requested` | `warning` | admin ตีกลับให้แก้ ยังไม่ปฏิเสธ |

สถานะเดิมที่ยังใช้: `Draft` `Sent` `Accepted` `Rejected` `Expired` `Converted` `Cancelled`

ฟังก์ชันที่ต้องเพิ่มใน `lib/workflows-outbound.tsx`

```
qtSubmit(qt, ctx)            Draft → Pending Approval          สิทธิ์: sale rep
qtApprove(qt, ctx)           Pending Approval → Approved       สิทธิ์: admin
qtReject(qt, ctx)            Pending Approval → Rejected       สิทธิ์: admin  (บังคับกรอกเหตุผล)
qtRequestRevision(qt, ctx)   Pending Approval → Draft          สิทธิ์: admin  (บังคับกรอกเหตุผล)
qtGeneratePdf(qt, ctx)       Approved ขึ้นไปเท่านั้น            สิทธิ์: ทั้งคู่
```

ฟังก์ชันเดิมที่ต้องแก้พฤติกรรม

- `qtSend` — เดิมเรียกได้จาก Draft ต้องเปลี่ยนเป็น **เรียกได้เฉพาะสถานะ Approved**
- `qtConvert` — เดิมสร้าง S/R ต้องเปลี่ยนเป็น **สร้าง S/O** และเรียกได้เฉพาะสถานะ `Accepted`

### 2.2 Sales Request

ใช้ของเดิมทั้งหมด ไม่ต้องแก้ state machine
เพิ่มเฉพาะกฎการอนุมัติราคาสองระดับ (ดูข้อ 3.2)

### 2.3 Sales Order

ใช้ของเดิม เพิ่มการตรวจซ้ำตอนสร้างตาม D5

## 3. กฎที่ต้อง implement

### 3.1 ล็อกใบหลังอนุมัติ

เมื่อสถานะเป็น `Approved` ขึ้นไป

- ทุกฟิลด์ในหัวเอกสารและทุกบรรทัดสินค้า อ่านอย่างเดียว
- ปุ่มแก้ไขหายไป เหลือแต่ปุ่ม "ขอแก้ไข"
- กด "ขอแก้ไข" → กลับเป็น `Draft` + `revision` เพิ่ม 1 + บันทึกใน `history[]` ว่าใครขอแก้และเพราะอะไร
- PDF ของ revision เดิมยังเปิดดูได้จากประวัติ

### 3.2 การอนุมัติราคาสองระดับ

ตามรูป — ใช้กับทั้ง QT และ S/R

```
ราคาที่เซลล์ใส่  >=  ราคาขั้นต่ำใน Price List   →  admin อนุมัติได้เอง
ราคาที่เซลล์ใส่  <   ราคาขั้นต่ำใน Price List   →  ต้องส่งต่อให้ Manager อนุมัติ
```

สิ่งที่ต้องเพิ่ม

- ฟิลด์ `floorPrice` (ราคาขั้นต่ำ) ในระดับบรรทัดของ Price List — ตอนนี้มีแค่ `rule.minMargin` กับ `rule.maxDiscount` ซึ่งเป็นระดับตารางไม่ใช่ระดับสินค้า
- ฟังก์ชัน `priceApprovalLevel(lines)` คืนค่า `"admin" | "manager"` โดยดูบรรทัดที่ต่ำที่สุด
- แสดงบนหน้าจอตอนเซลล์กรอกเลยว่า "ราคานี้ต้องให้ผู้จัดการอนุมัติ" ไม่ใช่ให้รู้ตอนถูกตีกลับ

### 3.3 คู่ค้าที่ยังไม่ยืนยัน

- เซลล์สร้างคู่ค้าใหม่ได้ → บันทึกด้วยสถานะ `Draft`
- คู่ค้าสถานะ `Draft` เปิด QT และ S/R ได้ แต่ **เปิด S/O ไม่ได้**
- admin เห็นรายการรอยืนยันในหน้าทำงานของตัวเอง
- เซลล์แก้ที่อยู่จัดส่งและเบอร์โทรของลูกค้าเก่าได้เอง (ตามรูป) แต่แก้ชื่อนิติบุคคลและเลขผู้เสียภาษีไม่ได้

### 3.4 ชื่อสินค้าและข้อความเพิ่มเติมระดับบรรทัด

ตามรูป ทั้ง QT และ S/R ต้องมี

- `customName` — ชื่อที่เซลล์พิมพ์เอง ใช้แทนชื่อสินค้ามาตรฐาน
- `lineNote` — ข้อความต่อท้าย เช่น "รับประกัน 2 ปี"
- checkbox ว่าจะให้ทั้งสองอย่างนี้ **ไปแสดงในบิล (D/O + Invoice)** หรือไม่

**หมายเหตุ: ฟิลด์ทั้งสามยังไม่มีใน data model** — `SrLine` ปัจจุบันมีแค่
`code, name, unit, qty, price, disc, tax, note`
ต้องเพิ่มและทำให้ไหลต่อไปถึง D/O และ Invoice

### 3.5 VAT / Non-VAT

ต้องเป็น toggle **ที่หัวเอกสาร** ของทั้ง QT, S/R, S/O
ตอนนี้ยังไม่มีฟิลด์นี้ในทั้งสามตัว มีแต่ `tax: 7` ระดับบรรทัด

- เลือก VAT → คำนวณภาษี + ตอนพิมพ์ออก 5 ชุด
- เลือก Non-VAT → ไม่คำนวณภาษี + ใช้แบบฟอร์มคนละแบบ

### 3.6 กรณีของไม่พอ

**ตอน S/R** — ถ้า available เป็น 0 ให้มีช่องกรอก "รอสินค้า" และ "รอกี่วัน" แล้วแสดงบนใบ

**ตอน Pick** — ตามรูป

| กรณี | สิ่งที่ต้องทำ |
|---|---|
| หยิบได้ครบ | tick all → ส่งได้ → ตัดสต๊อก |
| หยิบได้ไม่ครบ | ระบุจำนวนที่หยิบจริง → ส่วนที่เหลือเป็น back order หรือยกเลิก **ต้องบันทึกว่าลูกค้ายืนยันแล้ว ใครยืนยัน เมื่อไหร่** |
| ระบบว่ามีของ แต่ของจริงไม่มี | สร้างใบปรับยอดสต๊อกจากหน้า Pick → **ต้องผ่านการอนุมัติตามกฎเดิมของ Stock Adjustment** ห้ามปรับยอดตรงจากหน้า Pick |

> เตือน: อย่าทำปุ่ม force adjust ที่ปรับยอดได้ทันทีโดยไม่ผ่านอนุมัติ
> มันจะทำลายกฎ "ปรับยอดต้องมีเหตุผลและผู้อนุมัติ" ที่ระบบยึดอยู่ และทำให้ตัวเลขสต๊อกเชื่อถือไม่ได้อีกเลย

## 4. ลายเซ็นและตราประทับบน PDF

ยังไม่มีอะไรในระบบเลย ต้องคิดครบ 4 เรื่องนี้ก่อนเขียน

1. **เก็บไฟล์ลายเซ็นและตราประทับที่ไหน** → เสนอให้เก็บใน Company Settings ไม่ใช่ผูกกับผู้ใช้รายคน
2. **ใครมีสิทธิ์ทำให้มันปรากฏ** → เฉพาะคนที่กด approve เท่านั้น และต้องบันทึกชื่อคนนั้นลงบน PDF ด้วย
3. **PDF เก็บไว้ไหม** → ต้องเก็บ เพราะเป็นเอกสารที่ลูกค้าถืออยู่ ผูกกับ revision ของใบนั้น
4. **กันการปลอม** → อย่างน้อยต้องมีเลขที่เอกสาร + revision + วันเวลา + ชื่อผู้อนุมัติ พิมพ์อยู่บน PDF

## 5. ลำดับงานที่แนะนำ

ทำทีละขั้น แต่ละขั้นจบแล้วรันเทสต์ก่อนไปต่อ

| ขั้น | งาน | เหตุผล |
|---|---|---|
| 1 | เพิ่มสถานะใหม่ใน `QT_TONE` | เป็นรากของทุกอย่างที่เหลือ |
| 2 | เพิ่ม `qtSubmit` `qtApprove` `qtReject` `qtRequestRevision` | ทำ state machine ให้ครบก่อนทำหน้าจอ |
| 3 | แก้ `qtSend` ให้เรียกได้เฉพาะ Approved | กันไม่ให้ส่งใบที่ยังไม่อนุมัติออกไปหาลูกค้า |
| 4 | แก้ `qtConvert` ให้สร้าง S/O แทน S/R | ตาม D1 |
| 5 | ทำการล็อกใบหลัง approve + revision | ตาม D2 ถ้าไม่ทำขั้นนี้ ขั้น 6 ไม่มีความหมาย |
| 6 | ทำ PDF ลายเซ็น + ตราประทับ | ทำหลังล็อกใบแล้วเท่านั้น |
| 7 | เพิ่ม `customName` `lineNote` และ flag แสดงในบิล | ต้องไหลถึง D/O + Invoice ด้วย |
| 8 | เพิ่ม VAT / Non-VAT ที่หัวเอกสาร | กระทบการคำนวณและแบบฟอร์มพิมพ์ |
| 9 | ทำการอนุมัติราคาสองระดับ | ต้องมี `floorPrice` ใน Price List ก่อน |
| 10 | ทำสถานะรอยืนยันของคู่ค้าใหม่ | แยกออกมาได้ ไม่บล็อกงานอื่น |

## 6. เทสต์ที่ต้องเพิ่ม

repo มีเทสต์อยู่ 850 รายการใน 14 ไฟล์ ยังไม่มีไฟล์เทสต์ของ quotation
ควรเพิ่ม `tests/quotation.test.tsx` ที่ครอบคลุมอย่างน้อย

- Draft ส่งขออนุมัติได้ แต่ Pending Approval ส่งซ้ำไม่ได้
- ใบสถานะ Draft หรือ Pending Approval **กด Send ไม่ได้**
- ใบที่ยังไม่ approve **สร้าง PDF ไม่ได้**
- ใบสถานะ Approved **แก้ราคาไม่ได้**
- กดขอแก้ไขแล้ว revision เพิ่มขึ้น 1 และสถานะกลับเป็น Draft
- ปฏิเสธโดยไม่กรอกเหตุผลไม่ได้
- แปลงเป็น S/O ได้เฉพาะสถานะ Accepted เท่านั้น
- คู่ค้าสถานะ Draft เปิด S/O ไม่ได้ แต่เปิด QT ได้
- ราคาต่ำกว่า floorPrice ต้องได้ระดับอนุมัติเป็น manager

## 7. คำเตือนสำหรับตอนสั่งงาน Claude Code

- ให้ทำ **ทีละขั้นตามตารางข้อ 5** อย่าสั่งรวดเดียวทั้งหมด เพราะ 10 ขั้นนี้แตะไฟล์หลายสิบไฟล์

- หลังจบแต่ละขั้น สั่ง `npx tsc --noEmit` และ `npx vitest run` ทุกครั้ง
- repo นี้มี **commit เดียว** ทั้ง 117,000 บรรทัด — ให้ commit ก่อนเริ่มแก้ ไม่งั้นย้อนกลับไม่ได้
