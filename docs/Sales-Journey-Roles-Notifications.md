## 0. สรุปว่าเปลี่ยนอะไร

งานรอบนี้ทำให้ระบบเดินได้จริงแบบมีคนสามคนทำงานต่อกัน แทนที่จะเป็นหน้าจอที่ทุกคนเห็นเหมือนกันหมด

| เรื่อง | ตอนนี้ | ที่ต้องการ |
|---|---|---|
| บทบาท | มี 11 แต่ไม่มี "แอดมินรับออเดอร์" | เพิ่ม `SALES_ADMIN` |

| กล่องงาน | `dashPendingTasks()` นับจริงแต่ไม่กรองตามบทบาท | เห็นเฉพาะงานของตัวเอง |

## 1. การกลับคำตัดสิน D1 — QT ไปสร้าง S/R

ตอนขั้นที่ 4 เลือกให้ `qtConvert` สร้าง S/O ตรง รอบนี้กลับไปเป็น S/R

**แบบจำลองที่ถูกต้องคือ S/R เป็นด่านบังคับ ส่วน Quotation เป็นทางเลือก**
ตรงกับคอมเมนต์เดิมใน `data/sales-requests.ts` ที่เขียนว่า
`Quotation (optional) → Sales Request → Sales Order`

```
เส้นทาง 1  ลูกค้าขอใบเสนอราคา
  QT Draft → Pending Approval → Approved → Sent → Accepted → convert → SR

เส้นทาง 2  ลูกค้าไม่เอาใบเสนอราคา
  SR Draft โดยตรง

ทั้งสองเส้นทางมาบรรจบที่
  SR Submitted → Approved → convert → SO
```

### สิ่งที่ต้องแก้

- `qtConvert` กลับไปสร้าง S/R และเซ็ต `qt.srRef` เหมือนเดิม
- `qt.soRef` **เก็บฟิลด์ไว้ อย่าลบ** — ใบเก่าใน mock ที่ชี้ SO ต้องยังเปิดได้
  และ `qtTarget()` รองรับสองปลายทางอยู่แล้ว
- `createSalesOrderFrom` ยังอยู่ แต่เหลือผู้เรียกคนเดียวคือ `srConvert`
  เขียนคอมเมนต์ว่าเคยมีสองผู้เรียก และทำไมเหลือหนึ่ง
- ปุ่มใน `qtWorkflowActions` กลับเป็น "Convert to Sales Request"
- `billTypeDrift` ของ S/O: เส้นทางปกติจะเทียบกับ S/R เสมอ
  ส่วน `quotationRef` ยังใช้กับใบเก่า อย่าลบ

## 2. บทบาท — ต้องทำก่อนทุกอย่าง

ถ้าบทบาทยังไม่ถูก การแจ้งเตือนจะไม่รู้ว่าต้องส่งหาใคร ทำข้อนี้ก่อนเสมอ

### 2.1 เพิ่ม `SALES_ADMIN`

แอดมินรับออเดอร์ ไม่ใช่ผู้ดูแลระบบ ไม่ใช่หัวหน้าฝ่ายขาย

```
code       SALES_ADMIN
name       Sales Admin
desc       แอดมินฝ่ายขาย รับออเดอร์ อนุมัติเอกสารขายราคาปกติ
           คุมงานส่งของและวางบิล ไม่เห็นต้นทุนและกำไร
department Sales
scope      department
system     false
```

สิทธิ์ที่ต้องมี

| กลุ่ม | สิทธิ์ |
|---|---|
| Outbound ทั้งกลุ่ม | `ALL` (รวม approve) |
| `business-partner` | `view, create, edit, approve, export, print` — ยืนยันคู่ค้าได้ |
| `product` · `price-list` · `pricing` | `VIEW_ONLY` |
| `stock-inquiry` · `lot-tracking` · `serial-tracking` | `VIEW_ONLY` |
| `picking` · `packing` · `delivery-order` · `shipment` | `ALL` |
| `sales-invoice` · `credit-note` | `ALL` |
| Purchase · Inventory (แก้ไข) · Administration | ไม่มีสิทธิ์ |

`fields: []` — **ห้ามใส่ `cost` `margin` `profit`** แอดมินไม่ควรเห็นกำไร

> ข้อนี้ปิด backlog ข้อ 12 ด้วย: เดิมมีแค่ `SUPER_ADMIN` กับ `MANAGEMENT`
> ที่ยืนยันคู่ค้าได้ ซึ่งทำให้ MD กลายเป็นคอขวดของงานประจำวัน

### 2.2 ด่าน manager ต้องปฏิเสธได้จริง

ตอนนี้ `maySignAt("manager")` ผ่านทั้ง `SUPER_ADMIN` `MANAGEMENT` `SALES_MANAGER`
พอเพิ่ม `SALES_ADMIN` เข้ามา ด่านนี้จะเริ่มมีความหมายทันที เพราะเป็นบทบาทแรก
ที่มี `approve` แต่ **ไม่ควร** ผ่านระดับ manager

- `MANAGER_ROLES` คงเดิม: `["SALES_MANAGER", "MANAGEMENT"]`
- `SALES_ADMIN` ต้องไม่อยู่ในนั้น
- ต้องมีเทสต์ที่พิสูจน์ว่า `SALES_ADMIN` อนุมัติใบราคาปกติได้
  แต่อนุมัติใบที่ต่ำกว่า `price_last` **ไม่ได้** และข้อความบอกว่าต้องส่งให้ใคร

> ปิด backlog ข้อ 14 — เดิมด่านนี้ไม่ปฏิเสธใครได้เลย

### 2.3 ผู้ใช้ตัวอย่าง 3 คน

เพิ่มใน `data/admin.ts` ให้ครบสามบทบาทที่ flow ต้องใช้ พร้อมชื่อไทย
เพื่อให้เดโมอ่านรู้เรื่อง — `SALES_REP` · `SALES_ADMIN` · `SALES_MANAGER`

## 3. ปุ่มสลับบัญชี

`setCurrentUser(code)` มีอยู่แล้วใน `lib/domain/admin.ts:58` แต่ไม่มี UI เรียก

- วางบนแถบหัวเว็บ แสดงชื่อและบทบาทของคนที่ล็อกอินอยู่
- กดแล้วเลือกได้จาก 3 บัญชีตัวอย่าง
- สลับแล้วต้อง re-render ทั้งหน้า — เมนู สิทธิ์ กล่องงาน แจ้งเตือน เปลี่ยนตามทันที
- ทำเครื่องหมายให้ชัดว่าเป็นเครื่องมือสำหรับเดโม ไม่ใช่ฟีเจอร์จริง
  เขียนคอมเมนต์ว่าเมื่อมีระบบล็อกอินจริงต้องเอาออก

## 4. กล่องงานของฉัน

`dashPendingTasks()` ที่ `lib/domain/dashboard.ts:390` นับจากข้อมูลจริงอยู่แล้ว
แต่คืนงานทุกอย่างให้ทุกคนเหมือนกัน — ต้องกรองตามบทบาท

### กรองยังไง

กรองด้วย `can(moduleKey, action)` ของผู้ใช้ปัจจุบัน **ไม่ใช่เช็ครหัสบทบาทตรง ๆ**
วิธีนี้ทำให้เพิ่มบทบาทใหม่แล้วกล่องงานถูกต้องเองโดยไม่ต้องกลับมาแก้

### งานที่ต้องเพิ่มเข้ากล่อง

| งาน | ใครเห็น | เงื่อนไข |
|---|---|---|
| ใบเสนอราคารออนุมัติ | มี `quotation, approve` | `status = Pending Approval` |
| ใบเสนอราคารอลูกค้าตอบ | ผู้สร้างใบ | `status = Sent` |
| คำขอขายรออนุมัติ | มี `sales-request, approve` | `status = Submitted` |
| คำขอขายรอ manager | อยู่ใน `MANAGER_ROLES` | `Submitted` + `priceApprovalLevel = manager` |
| คู่ค้ารอยืนยัน | มี `business-partner, approve` | `status = Draft` |
| ใบสั่งขายรอจัดของ | มี `picking, create` | `status = Confirmed` |
| ใบส่งของรอวางบิล | มี `sales-invoice, create` | ส่งถึงแล้วยังไม่มีใบกำกับ |

**สำคัญ** — งานที่ต้องระดับ manager ต้องไม่โผล่ในกล่องของ `SALES_ADMIN`
ไม่งั้นเขาจะกดเข้าไปแล้วเจอว่าอนุมัติไม่ได้ ซึ่งแย่กว่าไม่เห็นเลย

## 5. ระบบแจ้งเตือน

ยังไม่มีอะไรในระบบ ต้องสร้างใหม่ทั้งชุด แต่ให้เล็กที่สุดที่ใช้งานได้

### 5.1 โครงข้อมูล

```ts
interface Notification {
  id: string;
  toRole: string;          // ส่งถึงบทบาทไหน
  toUser?: string;         // หรือถึงคนเจาะจง เช่น เจ้าของใบ
  kind: "approval_request" | "approved" | "rejected"
      | "revision_requested" | "converted" | "escalated";
  docType: string;         // "quotation" | "sales-request" | ...
  docCode: string;
  title: string;
  body: string;
  createdAt: string;
  createdBy: string;
  readAt?: string;
  href: string;            // กดแล้วไปหน้าเอกสารนั้น
}
```

เก็บใน array ในหน่วยความจำเหมือนข้อมูลอื่นทั้งระบบ

### 5.2 จุดที่ยิง

ยิงจาก **workflow function ที่จุดเปลี่ยนสถานะ** ไม่ใช่จากปุ่มบนหน้าจอ
เหตุผลเดียวกับที่ guard ต้องอยู่ที่จุดเขียนข้อมูล — ปุ่มมีหลายที่ workflow มีที่เดียว

| เหตุการณ์ | ส่งถึง | ข้อความ |
|---|---|---|
| `qtSubmit` | บทบาทที่มี `quotation, approve` | ใบเสนอราคา {code} รออนุมัติ |
| `qtApprove` | ผู้สร้างใบ | {code} อนุมัติแล้ว — ส่งให้ลูกค้าได้ |
| `qtReject` · `qtRequestRevision` | ผู้สร้างใบ | พร้อมเหตุผลที่กรอกไว้ |
| `srSubmit` ราคาปกติ | บทบาทที่มี `sales-request, approve` | คำขอขาย {code} รออนุมัติ |
| `srSubmit` ต่ำกว่า floor | `MANAGER_ROLES` เท่านั้น | ราคาต่ำกว่าขั้นต่ำ ต้องผู้จัดการอนุมัติ |
| `srApprove` | ผู้สร้าง | อนุมัติแล้ว — แปลงเป็นใบสั่งขายได้ |
| `srConvert` | ผู้สร้าง + บทบาทที่มี `picking, create` | ใบสั่งขาย {code} เปิดแล้ว |
| ยืนยันคู่ค้า | ผู้สร้างคู่ค้า | {ชื่อ} ยืนยันแล้ว — เปิดใบสั่งขายได้ |

**กฎที่ห้ามผิด** — คนที่กดปุ่มต้องไม่ได้รับแจ้งเตือนจากการกระทำของตัวเอง

### 5.3 หน้าจอ

- กระดิ่งบนแถบหัวเว็บ พร้อมตัวเลขที่ยังไม่ได้อ่าน
- กดแล้วเปิดรายการ กดรายการแล้วไปหน้าเอกสารและทำเครื่องหมายว่าอ่านแล้ว
- กรองตามผู้ใช้ปัจจุบัน: `toUser` ตรงกับตัวเอง **หรือ** `toRole` ตรงกับบทบาทตัวเอง

## 7. ของไม่พอ — รู้ให้เร็วขึ้น

ตอนนี้ `Partially Delivered` ถูกตั้งที่ `workflows-outbound.tsx:955` ตอนส่งของเท่านั้น
คือรู้ตอนของออกจากคลังไปแล้ว ซึ่งสายเกินไป

### ต้องเพิ่ม 2 จังหวะ

**จังหวะที่ 1 — ตอนยืนยันใบสั่งขาย (`soConfirm`)**
เรียก `availabilityFor()` ทุกบรรทัด ถ้ามีบรรทัดที่ของไม่พอ
ให้แสดง dialog ที่บอกรายการ จำนวนที่ขาด และให้เลือก

- เปิดเป็นของค้างส่ง — ยืนยันเฉพาะจำนวนที่มี ส่วนที่เหลือรอของเข้า
- ยกเลิกส่วนที่ขาด — ต้องระบุว่าลูกค้ายืนยันแล้ว ใครยืนยัน เมื่อไหร่
- ยกเลิกทั้งใบ

**จังหวะที่ 2 — ตอนหยิบของไม่ครบ**
มีอยู่แล้วบางส่วน ให้ทำให้สถานะใบสั่งขายเปลี่ยนเป็น `Partially Delivered` ทันที
พร้อมยอดค้างส่งที่ถูกต้อง และแจ้งเตือนกลับไปหาเซลล์เจ้าของใบ

> **ห้าม** สร้างปุ่มปรับยอดสต๊อกจากหน้าหยิบของ
> ถ้าของจริงไม่ตรงกับระบบ ให้ไปที่โมดูลปรับยอดสต๊อกตามปกติและรออนุมัติจริง

## 8. ลำดับงาน

ทำทีละขั้น จบแล้วหยุดรายงาน รัน `npx tsc --noEmit` และ `npx vitest run` ทุกขั้น

| ขั้น | งาน | ทำไมอยู่ตรงนี้ |
|---|---|---|
| N1 | เพิ่ม `SALES_ADMIN` + ผู้ใช้ตัวอย่าง 3 คน + ยืนยันด่าน manager ปฏิเสธได้ | รากของทุกอย่าง |
| N2 | ปุ่มสลับบัญชี | ต้องมีก่อนถึงจะทดสอบขั้นอื่นได้ |
| N3 | กล่องงานกรองตามบทบาท | ใช้ `can()` ไม่ใช่รหัสบทบาท |
| N4 | ระบบแจ้งเตือน — โครงข้อมูล + จุดยิง + กระดิ่ง | ยิงจาก workflow เท่านั้น |
| N5 | `qtConvert` กลับไปสร้าง S/R | แตะสายเอกสาร ทำหลังของอื่นนิ่งแล้ว |
| N6 | ของไม่พอ — เตือนตอนยืนยันใบสั่งขาย | ใหญ่สุด ทำท้าย |
| N7 | เทสต์เดินครบสายด้วยสามบัญชี | พิสูจน์ว่าต่อกันติดจริง |

## 9. สิ่งที่ห้ามพัง

งาน 11 ขั้นก่อนหน้าสร้างกฎเหล่านี้ไว้ ต้องยังทำงานหลังจบงานรอบนี้

- ใบที่อนุมัติแล้วแก้ไม่ได้ ต้องขอแก้ไขและได้ revision ใหม่
- snapshot ของ revision เก่าเป็น append-only ไม่มีใครเขียนทับได้
- ใบ Non VAT ทุกบรรทัดภาษี 0 และพิมพ์ได้เฉพาะฟอร์ม Non VAT
- สินค้าที่ไม่มีต้นทุนส่งขออนุมัติไม่ได้
- คู่ค้าสถานะ Draft เปิดใบสั่งขายไม่ได้
- ของติด QC Hold ขายไม่ได้
- ปรับยอดสต๊อกต้องมีเหตุผลและผู้อนุมัติ

## 10. คำเตือนสำหรับตอนสั่งงาน

- ทำทีละขั้น หยุดรายงานทุกขั้น
- ถ้าเทสต์เดิมพัง **ห้ามแก้เทสต์ให้ผ่าน** ให้หยุดรายงาน
- ถ้าเจอว่ามีของที่ทำเรื่องนั้นอยู่แล้วในโค้ด ให้รายงานก่อนสร้างใหม่
  งานรอบก่อนเจอแบบนี้ 4 ครั้ง และทุกครั้งของเดิมดีกว่าที่จะสร้างใหม่
- เพิ่มกฎใหม่ต้องมีเทสต์ที่พิสูจน์ว่ามีเคสที่ **ถูกปฏิเสธจริง**
  ไม่ใช่แค่เทสต์ว่าเคสที่ผ่านแล้วผ่าน — งานรอบก่อนเจอกฎที่ไม่กัดใครเลย 3 ครั้ง
